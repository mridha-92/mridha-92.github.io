### Executive Summary
Cyberpent has analyzed a user-reported spearphishing campaign targeting organizational VIPs that bypassed standard SPF authentication by routing through an intermediate Microsoft Exchange server. The attack leveraged a discrepancy in how intermediate mail hops evaluate SPF records across multi-layered email security architectures.

No user interaction or link clicks were reported, and initial endpoint verifications remain clean. The incident highlights potential anti-spam configuration gaps when utilizing a third-party anti-spam gateway in front of Microsoft 365 (M365) Defender policies.

### Technical Impact & Root Cause
**Root Cause:** The third-party anti-spam system evaluated SPF checks against the intermediate Microsoft Exchange server IP address rather than the original spoofed sender IP address. This misattribution allowed the email to pass third-party authentication checks.

**Technical Details:** 
* The original sender spoofed a domain on the initial hop, resulting in an internal `X-MS-Exchange-auth: SPF FAIL` and `ARC-Auth: Fail` status.
* Because the email traversed a Microsoft Exchange server before hitting the third-party security layer, the third-party tool checked the sender as the Exchange server, issuing an SPF "Pass".
* M365 anti-spam subsequently granted an SPF "Pass" upon receiving the email, as the connection originated directly from a valid Microsoft IP address.

### Mitigation & IOCs
To prevent spoofed emails from abusing intermediate Exchange hops, administrators should implement the following controls:
* Configure Defender Enhanced Filters (Enhanced Filtering for Connectors) in M365 to ensure Defender correctly identifies the original sender IP past the third-party gateway.
* Adjust third-party anti-spam rules and header parsing settings to evaluate the actual originating IP rather than intermediate relay or Exchange hosts.
